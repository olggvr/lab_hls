# ЛР №2: теория и шпаргалка к защите

Этот конспект описывает не абстрактную систему, а текущую реализацию проекта **School Platform**.
Команды для практической демонстрации находятся в `README.md`, а здесь собраны теория,
объяснение архитектурных решений и ответы на вероятные вопросы преподавателя.

## Если до защиты осталось 15 минут

Запомните восемь тезисов:

1. Монолит из ЛР №1 разделён по бизнес-ответственностям на `user`, `assignment`, `grades`
   и `message` services. У каждого сервиса своя PostgreSQL база.
2. Клиент обращается к системе через единую точку входа — Spring Cloud Gateway на порту 8080.
3. Сервисы регистрируются в Eureka. Gateway и межсервисные клиенты находят экземпляры по
   логическому имени, например `assignment-service`, а не по жёстко заданному IP.
4. Настройки лежат централизованно в `config-repo`: общие — в `common`, специфичные — в
   каталоге соответствующего приложения. Их раздаёт Spring Cloud Config Server.
5. `assignment-service` и `message-service` полностью реактивные: WebFlux + Reactor + R2DBC.
6. `grades-service` имеет реактивный WebFlux API, но хранит данные через блокирующий JPA/JDBC.
   Поэтому JPA и Feign вызовы выполняются на `Schedulers.boundedElastic()`, а не на event loop.
7. Между реактивными сервисами используется load-balanced `WebClient`. Feign используется
   в `grades-service → user-service`, чтобы выполнить отдельное требование задания.
8. Межсервисные вызовы защищены Resilience4j Circuit Breaker. При недоступности зависимости
   система либо возвращает управляемый HTTP 503, либо применяет допустимый fallback.

Короткая формулировка всей работы:

> Я декомпозировал школьный монолит по бизнес-контекстам, выделил отдельное владение данными,
> добавил service discovery через Eureka, централизованную конфигурацию, Gateway, HTTP-клиенты
> с Circuit Breaker и две модели реактивного доступа к данным: R2DBC и JPA,
> изолированный от event loop через boundedElastic.

## 1. Что такое микросервисная архитектура

Микросервис — автономное приложение, которое отвечает за ограниченную бизнес-область,
самостоятельно запускается и владеет своими данными. Сервисы взаимодействуют через явно
описанные сетевые контракты.

Главное отличие от обычного разбиения Java-кода на пакеты: вызов другого микросервиса — это
сетевой вызов. Он может быть медленным, завершиться по тайм-ауту или не выполниться вообще.
Поэтому появляются Eureka, Circuit Breaker, health checks и явные fallback-сценарии.

### Плюсы

- независимое масштабирование и развёртывание частей системы;
- изоляция ответственности и данных;
- отказ одного сервиса не обязан полностью останавливать систему;
- возможность выбирать подходящий стек данных для каждого контекста.

### Минусы

- сеть ненадёжна, нужны тайм-ауты и Circuit Breaker;
- сложнее отладка и эксплуатация;
- нет обычной транзакции сразу между несколькими сервисами;
- часть данных приходится дублировать;
- нужны discovery, gateway, централизованные настройки и наблюдаемость.

### Как выполнена декомпозиция

| Сервис | Бизнес-ответственность | Технология данных |
|---|---|---|
| `user-service` | пользователи, роли, учителя, ученики, родители, классы, предметы, нагрузка | Spring MVC + JPA/JDBC |
| `assignment-service` | домашние задания и решения учеников | WebFlux + Reactor + R2DBC |
| `grades-service` | оценки и сценарий уведомления об оценке | WebFlux + Reactor + JPA/JDBC |
| `message-service` | личные сообщения, рассылки, входящие и уведомления | WebFlux + Reactor + R2DBC |

Это разбиение близко к **bounded context** из Domain-Driven Design: внутри сервиса термины и
правила образуют связную предметную область. Например, `assignment-service` знает, как создать
задание и принять решение, но не управляет таблицей пользователей.

### Database per Service

У каждого бизнес-сервиса отдельная PostgreSQL база. Другой сервис не читает её таблицы напрямую,
а вызывает API владельца данных.

Например, `assignment-service` не делает SQL-запрос к таблице учителей. Он передаёт
`teacherId`, `classId`, `subjectId` в `user-service`, который проверяет учебную нагрузку и
возвращает подтверждённые данные.

Зачем это нужно:

- схема БД становится внутренней деталью сервиса;
- сервис можно менять и развёртывать независимо;
- нет общей БД, которая жёстко связывает все приложения;
- отказ или миграция одной БД меньше затрагивает остальные контексты.

Цена решения — межсервисные запросы и дублирование отображаемых данных. Например, в оценке
хранятся имя ученика, название задания и предмета. Это снимок данных на момент выставления
оценки. Если имя изменится, старый снимок автоматически не обновится — это осознанный компромисс.

## 2. Архитектура проекта

```text
                               Config Server :8888
                              /                   \
                    config-repo                   настройки всем

Клиент → API Gateway :8080 → Eureka/LoadBalancer → бизнес-сервис → своя БД
              │                                      │
              └──── единый Swagger                   └── HTTP-вызовы других сервисов

Eureka :8761 хранит реестр:
USER-SERVICE, ASSIGNMENT-SERVICE, GRADES-SERVICE,
MESSAGE-SERVICE, API-GATEWAY, CONFIG-SERVER
```

Всего в Docker Compose 11 контейнеров:

- 4 бизнес-сервиса;
- API Gateway, Config Server и Eureka Server;
- 4 независимых PostgreSQL.

### Путь обычного запроса

1. Клиент посылает запрос на `localhost:8080`.
2. Gateway сопоставляет URL с route predicate, например `/api/messages/**`.
3. URI вида `lb://message-service` означает поиск экземпляра по имени сервиса.
4. Spring Cloud LoadBalancer получает экземпляры из Eureka и выбирает один из них.
5. Запрос передаётся выбранному сервису.
6. Сервис выполняет бизнес-логику, при необходимости вызывает другой сервис и свою БД.
7. Ответ возвращается через Gateway клиенту.

Важно: Eureka сама не проксирует бизнес-запросы. Она только хранит реестр экземпляров.
Проксированием занимается Gateway, а выбором экземпляра — LoadBalancer.

## 3. Eureka и Service Discovery

Без discovery адреса пришлось бы задавать жёстко:

```text
http://10.0.0.17:8083
```

После перезапуска контейнера IP может измениться, а при масштабировании экземпляров станет
несколько. Eureka решает это через логическое имя:

```text
http://assignment-service
lb://assignment-service
```

### Как это работает

1. При старте Eureka Client регистрирует имя приложения, адрес, порт и статус.
2. Сервис периодически отправляет heartbeat.
3. Клиенты получают и кэшируют registry.
4. LoadBalancer выбирает доступный экземпляр нужного сервиса.
5. Если экземпляр перестаёт отправлять heartbeat, Eureka со временем исключает его.

Имя берётся из локального bootstrap-файла:

```yaml
spring:
  application:
    name: assignment-service
```

Eureka Server не регистрирует сам себя и не загружает registry, потому что в его конфигурации
установлены `register-with-eureka: false` и `fetch-registry: false`.

### Eureka и Docker DNS — не одно и то же

Docker DNS умеет разрешить имя контейнера внутри одной Docker network. Eureka дополнительно
даёт реестр приложений, статусы экземпляров и интеграцию со Spring Cloud LoadBalancer.
В проекте базы и инфраструктурные URL используют Docker DNS, а бизнес-маршрутизация через
Gateway и `WebClient` использует логические service IDs и Eureka.

## 4. Spring Cloud Config Server

Config Server выносит настройки из jar-файлов приложений. Это позволяет менять адреса,
тайм-ауты, параметры Circuit Breaker и маршруты централизованно.

### Структура конфигурации

```text
config-repo/
├── common/application.yml
├── api-gateway/application.yml
├── user-service/application.yml
├── assignment-service/application.yml
├── grades-service/application.yml
└── message-service/application.yml
```

`common/application.yml` содержит общие Eureka, Feign, Actuator и Resilience4j настройки.
Каталог конкретного приложения содержит его порт, подключение к БД и другие частные настройки.

Config Server настроен на:

```yaml
search-paths: common,{application}
```

Поэтому запрос `/assignment-service/default` объединяет настройки из `common` и
`assignment-service`.

В каждом сервисе локально остаётся только информация, необходимая для получения внешней
конфигурации:

```yaml
spring:
  application:
    name: assignment-service
  config:
    import: "optional:configserver:http://config-server:8888"
```

В Docker Config Server получает настоящий локальный Git-репозиторий: при сборке каталог
`config-repo` инициализируется и коммитится внутрь образа. Значит, используется Git backend,
а не просто чтение произвольных YAML-файлов.

`optional:` полезен для тестов и локальных переопределений: отсутствие Config Server само по
себе не останавливает bootstrap. Но в рабочем окружении без нужных настроек сервис всё равно
может не подключиться к БД или стартовать не на том порту.

## 5. Spring Cloud Gateway

Gateway — реактивный reverse proxy и единая внешняя точка входа. Клиенту не нужно знать порты
четырёх сервисов.

Маршрут состоит из:

- `id` — имя маршрута;
- `predicates` — условие выбора, здесь в основном `Path`;
- `uri: lb://...` — логическое имя сервиса с балансировкой;
- `filters` — преобразования запроса, например `StripPrefix` для документации.

Пример смысла маршрута:

```yaml
- id: message-service
  uri: lb://message-service
  predicates:
    - Path=/api/messages/**
```

Порядок маршрутов важен. Более конкретные пути оценок объявлены до общего
`/api/assignments/**` и catch-all `/api/**`, иначе запрос мог бы уйти не тому сервису.

Gateway также агрегирует OpenAPI четырёх сервисов в едином Swagger UI. Он не объединяет
бизнес-логику и не обращается к базам.

### Что Gateway даёт в промышленной системе

Кроме маршрутизации, здесь обычно размещают CORS, rate limiting, проверку токена, логирование,
correlation ID и общие фильтры. В этой лабораторной основной акцент — единая точка входа,
service discovery и Swagger.

## 6. Reactor: `Mono`, `Flux` и неблокирующая модель

Reactor реализует спецификацию Reactive Streams.

- `Mono<T>` — асинхронная последовательность из 0 или 1 элемента;
- `Flux<T>` — последовательность из 0, 1 или многих элементов;
- `Mono<Void>` — асинхронное завершение без тела ответа.

Publisher обычно **ленивый**: описание цепочки само по себе работу не запускает. Работа начинается,
когда появляется подписчик. В WebFlux подписывается сам фреймворк; вручную вызывать
`subscribe()` в контроллере не нужно.

### Основные операторы в проекте

| Оператор | Смысл |
|---|---|
| `map` | синхронно преобразовать уже полученное значение |
| `flatMap` | продолжить цепочку операцией, которая сама возвращает `Mono`/`Flux` |
| `flatMapMany` | перейти от одного значения к потоку многих |
| `zip` / `zipWith` | дождаться нескольких независимых результатов и объединить их |
| `switchIfEmpty` | заменить пустой publisher, например ошибкой `NotFoundException` |
| `thenMany` | дождаться завершения первой операции и продолжить другим `Flux` |
| `collectList` | собрать элементы `Flux` в `Mono<List<T>>` |
| `doOnNext` | выполнить побочный эффект без изменения значения, например поставить заголовок |
| `onError...` / fallback CB | управляемо обработать ошибку |

Ключевая разница:

```java
mono.map(value -> transform(value));          // transform возвращает обычный объект
mono.flatMap(value -> repository.save(value)); // save возвращает Mono
```

Если использовать `map` во втором случае, получится `Mono<Mono<T>>`.

### Backpressure

Backpressure — способность потребителя сообщить производителю, сколько элементов он готов
обработать. Это защищает медленного потребителя от неограниченного потока. Reactor и R2DBC
поддерживают этот протокол. Но если данные сначала собрать через `collectList`, потоковая
обработка для этой части заканчивается: список целиком окажется в памяти.

### Event loop и блокировки

WebFlux обслуживает много запросов небольшим числом event-loop потоков. Если заблокировать
такой поток JDBC-запросом, `sleep` или блокирующим HTTP-клиентом, пострадают многие запросы.
Поэтому внутри реактивной цепочки нельзя бездумно вызывать блокирующий код.

Также нельзя вызывать `.block()` в request path: это превращает асинхронную цепочку в
синхронное ожидание и может вызвать исчерпание потоков или deadlock.

## 7. R2DBC против JPA/JDBC

### JDBC/JPA

JDBC использует блокирующий вызов: поток ждёт, пока БД вернёт результат. JPA добавляет ORM,
entity lifecycle, dirty checking, связи и привычные `@Transactional` транзакции.

Плюсы: зрелая экосистема и удобная модель сложных сущностей. Минус для WebFlux: JDBC блокирует
поток.

### R2DBC

R2DBC — реактивный API доступа к реляционным БД. Репозитории возвращают `Mono` и `Flux`, а
ожидание сетевого ответа не удерживает request thread.

Плюсы: end-to-end неблокирующий pipeline и хорошая работа с большим числом одновременных I/O
операций. Минусы: менее богатая ORM-модель, чем JPA; связи и сложные агрегаты чаще собираются
явно.

### Как это показано в проекте

`assignment-service` и `message-service`:

```text
WebFlux → Reactor → ReactiveCrudRepository → R2DBC PostgreSQL
```

Это полностью реактивный путь.

`grades-service`:

```text
WebFlux → Reactor → fromCallable → boundedElastic → JPA/JDBC → PostgreSQL
```

Сам факт возврата `Mono` не делает JPA неблокирующим. Поэтому блокирующая работа оборачивается:

```java
Mono.fromCallable(() -> persistenceService.save(...))
    .subscribeOn(Schedulers.boundedElastic())
```

`boundedElastic` — ограниченный пул потоков для блокирующих I/O-задач. Он сохраняет реактивный
API и не блокирует event loop, но не превращает JDBC в R2DBC. Это **мост между моделями**, а
не магическое неблокирующее JPA.

`user-service` также использует JPA. Его внутренние методы, вызываемые реактивными сервисами,
возвращают `Mono`, а JPA-логику выполняют на `boundedElastic`.

## 8. Межсервисные клиенты: WebClient и Feign

### Load-balanced WebClient

В реактивных сервисах создаётся `WebClient.Builder` с `@LoadBalanced`. Поэтому URL:

```text
http://user-service/internal/directory
```

трактуется не как обычное DNS-имя, а как service ID. Spring Cloud LoadBalancer получает
экземпляры из Eureka и подставляет реальный адрес.

`WebClient` неблокирующий и возвращает `Mono`/`Flux`, поэтому подходит для WebFlux pipeline.

Он используется в цепочках:

- `assignment-service → user-service`;
- `message-service → user-service`;
- `grades-service → assignment-service`;
- `grades-service → message-service`.

### OpenFeign

Feign — декларативный HTTP-клиент. Разработчик описывает Java-интерфейс с аннотациями, а
реализацию запроса генерирует Spring Cloud OpenFeign.

В проекте:

```java
@FeignClient(name = "user-service",
             path = "/internal/directory",
             fallback = UserClientFallback.class)
interface UserClient { ... }
```

Он используется в `grades-service → user-service`. Feign здесь блокирующий, поэтому вызов
оборачивается в `Mono.fromCallable(...).subscribeOn(boundedElastic())`.

Почему это соответствует замечанию «если оба сервиса реактивные, клиент должен быть
реактивным»: между полностью реактивными `assignment`, `message` и реактивным API `grades`
используется `WebClient`. Feign направлен к `user-service`, основной стек которого MVC + JPA,
а его блокировка явно изолирована.

### Почему не передавать JPA entity по сети

Между сервисами передаются отдельные request/response DTO. Entity — внутренняя модель хранения.
Если отдавать entity, сетевой контракт начнёт зависеть от схемы БД и ORM-аннотаций.

## 9. Circuit Breaker и отказоустойчивость

Circuit Breaker предотвращает бесконечные вызовы уже неработающей зависимости.

### Состояния

1. `CLOSED` — вызовы проходят, ошибки считаются.
2. Если ошибок слишком много, состояние переходит в `OPEN`.
3. В `OPEN` новые вызовы быстро отклоняются без сетевого ожидания.
4. Через заданное время состояние становится `HALF_OPEN`.
5. Пропускается несколько пробных запросов.
6. При успехе — обратно `CLOSED`, при ошибках — снова `OPEN`.

Параметры проекта:

- окно: 10 вызовов;
- минимум для расчёта: 5 вызовов;
- порог ошибок: 50%;
- ожидание в `OPEN`: 10 секунд;
- пробных вызовов в `HALF_OPEN`: 3.

Пример: после пяти вызовов, если как минимум половина завершилась ошибкой, breaker может
открыться. До пяти вызовов статистики недостаточно.

### Circuit Breaker не равен timeout и retry

- timeout ограничивает длительность одного вызова;
- retry повторяет отдельный неуспешный вызов;
- Circuit Breaker прекращает поток бесполезных вызовов к деградировавшей зависимости.

Неосторожный retry может усилить аварию: каждый пользовательский запрос создаст ещё несколько
запросов к уже перегруженному сервису.

### Fallback в проекте

- Если `user-service` недоступен при создании задания или сообщения, возвращается управляемый
  `503 Service Unavailable`.
- Если `assignment-service` недоступен при выставлении оценки, возвращается 503: без решения
  ученика оценку создавать нельзя.
- Если `user-service` недоступен для Feign, `UserClientFallback` также приводит к 503.
- Если оценка сохранена, но `message-service` недоступен, grades-service возвращает результат
  с `notificationId = null` и количеством уведомлённых адресатов `0`. Во внутреннем ответе
  клиента также стоит `delivered = false`. Это graceful degradation: основная операция
  выполнена, вторичная временно недоступна.

HTTP 503 выбран потому, что проблема временная и находится в зависимом сервисе, а не в
валидации запроса клиента.

## 10. Главные бизнес-сценарии

### Создание задания

```text
Клиент
  → Gateway
  → Assignment Service
  → User Service: существует ли учитель и ведёт ли предмет в классе?
  → Assignment DB: сохранить задание через R2DBC
  → 201 Created
```

Здесь `assignment-service` не доверяет одним входным ID и проверяет их у владельца справочных
данных. Ответ User Service также содержит имена класса, учителя и предмета для локального снимка.

### Отправка решения

1. Проверяется существование задания.
2. User Service подтверждает ученика и его принадлежность нужному классу.
3. Проверяется, что ученик ещё не отправлял решение этого задания.
4. Решение сохраняется в реактивной транзакции.
5. Повторная отправка приводит к HTTP 409 Conflict.

### Выставление оценки

```text
Клиент
  → Gateway
  → Grades Service
      → Assignment Service через reactive WebClient: получить решение и контекст задания
      → User Service через Feign: получить ученика и родителей-адресатов
      → Grades DB через JPA на boundedElastic: сохранить оценку
      → Message Service через reactive WebClient: отправить уведомление
  → результат оценки + результат уведомления
```

Для объединения контекста задания и аудитории используется `zipWith`. Затем `flatMap`
последовательно сохраняет оценку и запускает уведомление.

### Просмотр оценок

Grades Service спрашивает User Service, какой scope разрешён пользователю:

- `STUDENT` — собственный student ID;
- `PARENT` — IDs его детей;
- `TEACHER` — teacher ID;
- `SUPERVISOR` — сценарий отклоняется бизнес-ошибкой.

После этого JPA выбирает оценки только в разрешённой области.

## 11. Транзакции и согласованность

Локальная транзакция работает только внутри одного сервиса и одной БД:

- submission сохраняется через reactive `TransactionalOperator`;
- сообщение и адресаты сохраняются одной реактивной транзакцией;
- оценка сохраняется обычной JPA-транзакцией с `@Transactional`.

Одна ACID-транзакция не охватывает Grades DB и Message DB. Поэтому возможна ситуация:
оценка сохранена, а уведомление не отправлено. Текущая политика — сохранить основной результат
и вернуть признак неуспешного уведомления.

В production это часто улучшают паттерном **Transactional Outbox**:

1. оценка и событие `GradeCreated` сохраняются в одной локальной транзакции;
2. отдельный publisher гарантированно отправляет событие в брокер;
3. Message Service идемпотентно обрабатывает событие;
4. повторная доставка не создаёт дубликаты.

Для лабораторной используется синхронный HTTP — он проще и явно демонстрирует Feign,
WebClient и Circuit Breaker.

---

## 12. Почему два сервиса над двумя assignment-репозиториями

После замечания преподавателя доступ разделён:

- `AssignmentService` работает с `AssignmentRepository`;
- `SubmissionService` работает с `SubmissionRepository` и обращается к `AssignmentService`
  за проверкой задания.

Так соблюдается Single Responsibility Principle: CRUD заданий и жизненный цикл решений —
разные обязанности. Один огромный сервис не знает детали обоих репозиториев сразу.

Это сервисы внутри одного микросервиса, а не два отдельных deployable-приложения. Требование
касалось разделения service layer по репозиториям, а не создания ещё двух сетевых приложений.

## 13. Почему нет `ResponseEntity` в реактивных контроллерах

Контроллер возвращает сам publisher:

```java
public Mono<AssignmentResponse> create(...) { ... }
public Flux<SubmissionResponse> submissions(...) { ... }
public Mono<Void> delete(...) { ... }
```

Статический HTTP-статус задаётся через `@ResponseStatus`, например 201 или 204. Ошибки
преобразуются в статус и реактивное тело через `@RestControllerAdvice`.

Для динамического заголовка пагинации контроллер получает `ServerHttpResponse`, ставит
`X-Total-Count` через `doOnNext`, но всё равно возвращает `Mono<List<...>>`, а не
`ResponseEntity`.

Возврат `Mono<ResponseEntity<T>>` технически возможен, но в этой реализации не нужен.

## 14. Пагинация

В Assignment Service реализовано два варианта.

### Offset pagination

```text
page=3&size=20
```

Понятна пользователю и позволяет перейти на конкретную страницу. Но на больших таблицах
`OFFSET` может быть дорогим, а параллельные вставки способны сдвинуть результаты.

### Cursor pagination

```text
cursor=последний_увиденный_id&size=20
```

Следующая выборка использует условие `id < cursor`, получает `size + 1` записей и по лишней
записи определяет `hasNext`. Такой подход устойчивее к новым вставкам и обычно быстрее на
больших данных при наличии индекса.

Размер ограничивается диапазоном 1–50, чтобы клиент не запросил слишком большой ответ.

## 15. Миграции и инициализация БД

JPA-сервисы используют Liquibase:

- `user-service` — схема, справочные и demo-данные;
- `grades-service` — схема оценок;
- Hibernate работает с `ddl-auto: validate`, то есть проверяет схему, но не создаёт её сам.

R2DBC-сервисы используют SQL initialization (`spring.sql.init.mode: always`) и файлы
`schema.sql`/`data.sql`.

Преимущество управляемых миграций: схема воспроизводима, изменения версионируются, а запуск
не зависит от ручного создания таблиц.

## 16. Docker Compose

Все контейнеры находятся в сети `school-net`. Имена compose-сервисов работают как DNS-имена
внутри сети, например `user-db` и `config-server`.

### Healthcheck и depends_on

Бизнес-сервис запускается только после healthy-состояния своей БД и Config Server.
Gateway ждёт бизнес-сервисы. Это упорядочивает старт.

`depends_on` не обеспечивает отказоустойчивость после запуска. Если зависимость упала позже,
с этим работают timeouts, Eureka и Circuit Breaker.

### Volumes

Четыре named volume сохраняют данные PostgreSQL между `docker compose down` и следующим
запуском. Команда `docker compose down -v` удаляет volumes и полностью сбрасывает данные.

### Multi-stage build

В build stage Maven на JDK 21 создаёт jar. В runtime stage остаются только JRE, jar и
непривилегированный пользователь. Это уменьшает образ и поверхность атаки.

## 17. Тестирование и покрытие

Используются несколько уровней тестов.

### Unit tests

Mockito подменяет репозитории и зависимости. Такие тесты быстрые и проверяют отдельную
бизнес-ветку: конфликт, выбор scope, сохранение или fallback.

### Интеграционные тесты

`@SpringBootTest` поднимает Spring context. Testcontainers запускает настоящий PostgreSQL
16.4, поэтому проверяется реальная совместимость SQL, JPA, Liquibase и R2DBC, а не поведение
in-memory базы с другой семантикой.

- MVC API `user-service` проверяется через MockMvc;
- реактивные цепочки проверяются через Reactor Test `StepVerifier`;
- межсервисные HTTP-клиенты проверяются отдельно, включая fallback.

`StepVerifier` подписывается на publisher, проверяет последовательность значений, ошибку и
факт завершения. Это надёжнее ручного вызова `.block()` в тестах реактивной логики.

### JaCoCo

На фазе `verify` JaCoCo строит отчёт и требует не менее 70% line coverage сервисного слоя.
Coverage показывает, какие строки выполнялись, но не гарантирует качество assert'ов и полноту
бизнес-сценариев. Поэтому важны и позитивные, и негативные тесты.

### Почему тестам нужен Docker

Testcontainers управляет временными контейнерами через Docker API. Если Docker Desktop
выключен, интеграционные тесты падают с `Could not find a valid Docker environment`.
Это проблема окружения, а не бизнес-кода.

Maven Toolchains автоматически выбирает установленный JDK 21 для compiler и Surefire, даже
если сам Maven запущен на более новой Java.

## 18. HTTP-статусы, которые стоит уметь объяснить

| Статус | Когда применяется |
|---|---|
| `200 OK` | успешное чтение или обновление |
| `201 Created` | создано задание, решение или сообщение |
| `204 No Content` | успешное удаление без тела |
| `400 Bad Request` | не прошла валидация DTO или нарушено бизнес-условие запроса |
| `404 Not Found` | сущность не найдена |
| `409 Conflict` | ресурс конфликтует с текущим состоянием, например повторная сдача |
| `503 Service Unavailable` | временно недоступен зависимый микросервис |

DTO валидируются через Jakarta Validation (`@Valid`, `@NotBlank`, `@Min`, `@Positive` и т. п.).
Глобальные exception handlers формируют единый JSON ошибки.

## 20. Частые вопросы преподавателя и короткие ответы

### «Почему это микросервисы, а не просто несколько модулей?»

Каждый бизнес-сервис — отдельное Spring Boot приложение, отдельный jar и контейнер со своим
портом и своей БД. Связь идёт по HTTP, а не прямым вызовом Java-метода.

### «Почему не оставить одну общую БД?»

Общая БД связывает схемы и релизы всех сервисов. Database per Service сохраняет автономность;
владелец данных предоставляет API-контракт.

### «Что делает Eureka?»

Хранит динамический реестр service ID → instances. Она не проксирует запросы. Экземпляр
выбирает LoadBalancer, а внешний запрос проксирует Gateway.

### «Что означает `lb://`?»

Нужно разрешить логическое имя через Spring Cloud LoadBalancer и выбрать экземпляр из registry.

### «Зачем Config Server, если есть environment variables?»

Environment variables переопределяют секреты и параметры окружения, а Config Server хранит
общие версионируемые настройки приложений. Они дополняют друг друга.

### «Чем WebClient лучше RestTemplate в реактивном сервисе?»

WebClient не блокирует поток ожиданием ответа и возвращает `Mono`/`Flux`. RestTemplate и
обычный Feign блокируют вызывающий поток.

### «Почему в проекте всё-таки есть Feign?»

Это отдельное требование ЛР. Он используется декларативно для вызова MVC/JPA User Service,
а блокировка изолирована на boundedElastic. Между полностью реактивными частями используется
WebClient.

### «JPA внутри `Mono` стало реактивным?»

Нет. JPA остаётся блокирующим. `fromCallable + boundedElastic` лишь не даёт ему заблокировать
event loop и позволяет встроить результат в Reactor pipeline.

### «Почему нельзя выполнять JPA прямо в `map`?»

`map` выполнится на текущем потоке, которым может быть Netty event loop. Блокирующий JDBC
остановит этот поток и ухудшит обработку всех запросов на нём.

### «Circuit Breaker и fallback — одно и то же?»

Нет. Breaker решает, пропускать ли вызов, на основе статистики отказов. Fallback определяет,
какой результат или ошибку вернуть, если вызов не выполнен.

### «Почему на недоступность зависимости возвращается 503?»

Запрос может быть корректным, но сервис временно не может его завершить из-за зависимости.
503 точнее, чем 400 или необработанный 500.

### «Что будет, если оценка сохранится, а уведомление упадёт?»

Оценка останется, ответ покажет, что уведомление не отправлено. Общей транзакции между БД нет.
Для гарантированной доставки в production нужен Outbox и брокер сообщений.

### «Что обеспечивает `@Transactional`?»

Атомарность операций только в рамках локального transaction manager и одной БД. Он не
откатывает изменения в другом микросервисе.

### «Почему cursor pagination лучше offset?»

Не требует пропускать большое число строк и устойчивее к вставкам между запросами. Зато нельзя
так же просто перейти на произвольный номер страницы.

### «Зачем Testcontainers, если можно H2?»

H2 отличается от PostgreSQL SQL-диалектом, типами и поведением. Testcontainers проверяет код
на той же СУБД, что используется приложением.

### «Что такое cold publisher?»

Publisher, который начинает работу заново для каждого подписчика. Большинство цепочек
`Mono`/`Flux` в WebFlux именно такие. Без подписки запрос к БД или HTTP обычно не выполнится.

### «Что такое backpressure?»

Механизм, позволяющий потребителю ограничивать скорость производителя, чтобы не переполнить
память и не захлебнуться потоком данных.

### «Зачем отдельные internal endpoints?»

Это API для взаимодействия сервисов, отделённое по URL от внешнего `/api`. Gateway не
маршрутизирует их клиенту. В production дополнительно нужна сетевая политика или service auth.

## 21. Честные ограничения текущей реализации

Если преподаватель спросит о production-ready уровне, не утверждайте, что реализовано то,
чего нет. Лучше назвать ограничение и способ развития:

- нет полноценной аутентификации JWT/OAuth2 и Spring Security;
- internal endpoints логически скрыты Gateway, но не защищены отдельной service authentication;
- межсервисное взаимодействие синхронное, брокера и Outbox нет;
- нет distributed tracing и correlation ID;
- Config Server содержит snapshot Git-репозитория внутри образа, а не внешний Git hosting;
- нет нескольких экземпляров Eureka/Gateway, поэтому инфраструктура не высокодоступна;
- fallback уведомления не ставит автоматическую задачу на повторную доставку;
- дублированные display-поля между сервисами дают eventual consistency.

Хорошая формулировка:

> Для лабораторной реализованы требуемые паттерны и воспроизводимый стенд. Для production я бы
> добавил security, tracing, внешний config repository, Outbox с брокером, идемпотентность и
> несколько экземпляров инфраструктурных компонентов.

> блокируют event loop, а блокирующие JPA и Feign вызовы явно изолированы.

## 23. Термины в одну строку

- **API Gateway** — единая входная точка и reverse proxy.
- **Service Discovery** — динамический поиск экземпляра сервиса по логическому имени.
- **Eureka** — registry server/client для discovery.
- **Load Balancer** — выбирает экземпляр одного сервиса.
- **Config Server** — централизованно раздаёт внешние настройки.
- **Feign** — декларативный, в этой реализации блокирующий HTTP-клиент.
- **WebClient** — неблокирующий HTTP-клиент Spring WebFlux.
- **Circuit Breaker** — временно прекращает вызовы деградировавшей зависимости.
- **Fallback** — запасной результат или управляемая ошибка.
- **Reactor** — библиотека реактивных потоков `Mono`/`Flux`.
- **R2DBC** — неблокирующий доступ к реляционной БД.
- **JPA** — ORM-спецификация поверх блокирующего JDBC.
- **boundedElastic** — ограниченный scheduler для блокирующих задач.
- **Backpressure** — управление скоростью производителя со стороны потребителя.
- **DTO** — внешний контракт передачи данных, отделённый от entity.
- **Database per Service** — каждый сервис владеет своей БД.
- **Eventual consistency** — данные между сервисами становятся согласованными не обязательно мгновенно.
- **Testcontainers** — запуск реальных зависимостей в Docker для интеграционных тестов.
- **Actuator** — технические endpoints состояния и метрик Spring Boot приложения.
